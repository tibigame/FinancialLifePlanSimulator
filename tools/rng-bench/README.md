# 乱数の設計と実機測定

## 実装

アプリ本体の `src-tauri/src/rand` をそのまま読み込んで測定する独立したCargoプロジェクトです。Tauri全体をバックエンドごとに再ビルドせず、アプリと同じ乱数コードを検証します。依存バージョンは両方のCargo.lockに記録しています。

- 設定の `fix_random_seed` は初期値true。既存の設定ファイルに項目がなくてもtrueになります。
- 固定時のシードは `[42u8; 32]`。非固定時は `SysRng.try_fill_bytes` で32バイト取得します。OS乱数の失敗はResultで返します。
- アプリ起動時に生成スレッドを開始します。シード取得とバッファ確保は呼び出し元、ChaCha12Rngの初期化と乱数の生成は生成スレッドで行います。
- 80,000バイト（u64 10,000個相当）のバッファを2面だけ確保して再利用します。利用側には受信したVecの所有権を渡し、使い切った面を生成側へ返します。準備済み・返却用チャネルの容量はそれぞれ1です。
- 2面目は最初から先行生成し、その後も返却された面をすぐに補充します。9,900個などの閾値は不要です。補充が間に合わなければバッファ境界で待ちます。
- バッファ補充では再シードせず、同じChaCha12Rngの続きから生成します。型変換のバイト順はlittle endianに固定し、未使用バイトを捨てません。
- 設定変更の保存時は、新しいRNGを準備してから設定を保存し、成功後に置き換えます。ログ件数だけの変更では乱数列をリセットしません。
- アプリ状態にあるMutexは、設定変更時などの所有者間の調整用です。`SystemRandom`自身は単一消費者向けの `&mut self` APIで、各値の取得にMutexを使用しません。
- 終了時は両チャネルを切断してから生成スレッドをjoinします。未消費のバッファがあっても終了できます。

シミュレーション本体はまだありません。将来、実行開始時に設定に従ってRNGを作成し、そのシミュレーションスレッドで所有してください。同じシードでも既存RNGを継続利用すれば乱数列は続きからになります。再実行時に `new(true)` または保存したシードを使う `from_seed` を呼ぶと、先頭から再現できます。

```rust
use financiallifeplansimulator_lib::rand::SystemRandom;

fn example() -> std::io::Result<()> {
    let mut random = SystemRandom::new(true)?;
    let values = random.get::<u16>(10)?; // 正確に20バイトを消費
    assert_eq!(values.len(), 10);

    let mut reused = [0u64; 10_000];
    random.fill(&mut reused)?; // 配列を再利用し、取得ごとの確保を避ける

    let mut bytes = [0u8; 3];
    random.fill_bytes(&mut bytes)?; // 残りのバイトも次の取得で利用する
    Ok(())
}
```

対応型はu8/u16/u32/u64/u128と同じ幅の符号付き整数です。boolや浮動小数点のビット列への変換は提供しません。確率・範囲・正規分布の生成は別の層で扱います。シード、ライブラリ版、分布変換の実装・呼び出し順も再現条件です。読み取り時の生成スレッド切断はResultで通知します。その場合、呼び出し先の配列は部分的に更新されている可能性があります。

## CPU命令の調査

実機: AMD Ryzen 9 7950X、Windows x86_64、rustc 1.99.0 (b940084d7 2026-09-28)。2026-10-08測定。

`is_x86_feature_detected!` によるCPU・OS対応の判定結果:

```text
sse2=true
avx2=true
avx512f=true
avx512vl=true
avx512bw=true
```

Zen 4のAVX-512対応はAMD資料にも記載されています。ただし、CPU対応と利用ライブラリの対応は別です。

採用した **chacha20 0.10.2のChaCha12RngはAVX-512を使用しません**。配布クレートの `src/rng.rs`、`Generator::generate` に以下の分岐があります。

```rust
// AVX-512 doesn't support RNG, so use AVX-2 instead
if #[cfg(any(chacha20_backend = "avx2", chacha20_backend = "avx512"))] {
```

暗号化用ChaChaにはAVX-512実装がありますが、RNG用の出力生成はAVX2です。したがって、AVX-512フラグでビルドして得た値を「AVX-512のRNG性能」として比較してはいけません。今回はChaCha12Rngを維持し、AVX2を利用します。

通常のアプリビルドはバックエンド強制フラグなし。x86/x86_64ではライブラリが実行時にAVX2、SSE2、ソフトウェア実装の順に選択します。`target-cpu=native` や `target-feature=+avx2` を実行ファイル全体に設定していません。AVX2/AVX-512のないマシンでも動く構成です。ただし非対応CPU実機での起動確認は未実施で、今回は同じCPU上でフォールバック実装を強制して検証しました。

参考:

- [AMD Zen 4アーキテクチャ資料](https://docs.amd.com/api/khub/documents/Fk9hEabDNdOiD4PcQu7EYw/content)
- [chacha20のバックエンド設定](https://docs.rs/chacha20/0.10.2/chacha20/#configuration-flags)

## 測定方法と結果

1回の取得量はu64 10,000個相当、80,000バイトです。release、opt-level=3、LTO有効、codegen-units=1。各方式を100回ウォームアップしてから、1,000回の連続処理を11回測定し、1回あたり時間の中央値を記録しました。`black_box` で出力の最適化除去を防止します。

通常の4項目はシード取得・スレッド起動を除いた定常状態です。ダブルバッファでは先行生成済みの2面だけを測ることを避け、継続的な補充・待機・コピーを含めます。別途、固定シードでの起動から初回get完了までを101回測定しました（終了処理は除外）。非固定時のOSシード取得時間は測定していません。スレッドをコアに固定せず、通常のWindowsスケジューラ上で測定しています。

| 方式 | 自動選択（実機ではAVX2） | SSE2強制 | soft強制 |
|---|---:|---:|---:|
| ChaCha12Rng直接 fill_bytes | 15.778 µs | 22.689 µs | 50.610 µs |
| ダブルバッファ fill_bytes | 19.049 µs | 24.391 µs | 52.477 µs |
| ダブルバッファ fill u64 | 18.285 µs | 25.738 µs | 52.345 µs |
| ダブルバッファ get u64（Vec確保込み） | 21.308 µs | 29.212 µs | 52.403 µs |
| 起動＋初回get（固定シード） | 83.000 µs | 104.400 µs | 133.900 µs |

AVX2はsoftに対し、直接生成で約3.21倍、getで約2.46倍でした。SSE2との直接生成の差は約1.44倍です。softは専用SIMDバックエンドを使わない実装であり、コンパイラがx86_64の標準命令（SSE2など）まで一切使わないという意味ではありません。

この連続取得だけの測定では、ダブルバッファは直接生成より遅い結果です。シミュレーション計算との並行実行による効果はまだ測定していません。80,000バイトは最適値と確定したものではありません。`get`は便利ですが、繰り返し呼ぶ場合は `fill` で出力配列も再利用する方が確保の負担を減らせます。

3バックエンドとも、アプリと共有する乱数テスト5件およびClippyを通過しました。320,000バイトの参照乱数列との一致と、バックエンド間のfingerprint `e491fb6f3aac979e` の一致も確認しています。数値はこのマシンの測定値で、他の負荷・CPU・OSでは変動します。[CSV](results-2026-10-08.csv)にも保存しています。

## 再実行

リポジトリ直下で以下を実行します。署名を必須とする環境では、このプロセスだけ実行ポリシーを指定します。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/rng-bench/run.ps1
```

スクリプトはauto、sse2、softを順にビルド・テスト・Clippy検証・測定します。バックエンド指定はベンチマーク用プロセスの環境変数だけに適用し、終了時に元に戻します。成果物は `src-tauri/target/rng-bench/` に分離し、通常のアプリビルドを変更しません。
